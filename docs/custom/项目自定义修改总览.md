# 项目自定义修改总览

## 1. 项目身份

- Upstream：`marktext/marktext`
- Fork：`Ember-Dawn/marktext`
- 当前主要分支：`main`
- 当前基线版本：**MarkText v0.19.1**
- 主要目标平台：Windows 11 x64
- 核心原则：**稳定与性能优先，定制功能尽量以最小侵入方式实现**

当前 `main` 不是以 upstream 最新 `develop` 为基线，而是主动选定 v0.19.1 作为稳定开发基线。

## 2. 为什么选择 v0.19.1

曾经基于后续 `develop / 0.20.0-dev` 进行定制，但实际使用中出现 Markdown 打开和多标签切换明显变慢的问题。

重新测试纯净 v0.19.1 后，`pnpm run dev` 下的编辑、打开文件和标签切换速度恢复正常，因此决定：

> 后续个人定制优先建立在 v0.19.1 上，并把性能作为重要验收指标。

这意味着后续实现任何 UI 功能时，都应避免无必要的持续 watcher、重复计算、隐藏但仍挂载的大型组件，以及影响标签切换路径的重逻辑。

### 3.3 文件保存与 Watcher 自触发修复

状态：**已实现并完成 DEV 实测**

问题表现是在 Windows，尤其 OneDrive 等同步目录中，MarkText 对已打开 Markdown 执行 Ctrl+S 后，文件 watcher 可能把 MarkText 自己的保存再次当作外部磁盘修改，从而错误显示：

```text
"<filename>" has been changed on disk. Do you want to reload it?
```

实际诊断确认：同一个文件不存在重复 file watcher，但一次 MarkText 保存可以产生多个 `change` 事件。旧的“一次保存只忽略下一次 change”机制在第一个事件后就会耗尽，因此第二个事件会漏出并触发 Reload 提示。

当前修复原则：

- Windows 路径先规范化，避免盘符大小写或路径表现形式导致同一文件匹配失败；
- self-save 信息在真正写磁盘前登记，避免写入与 watcher 之间的竞争；
- 使用刚保存 Markdown 内容的 SHA-256 fingerprint 识别 self-save；
- self-save fingerprint 在短时间窗口内保留，以吸收 OneDrive 等环境对同一次保存产生的多个重复事件；
- 只有 watcher 读到的磁盘内容仍与 MarkText 刚保存内容完全一致时才忽略；
- 一旦磁盘内容 fingerprint 不同，立即按真实外部修改处理，不通过简单延长 timeout 吞掉外部编辑；
- 保存失败时撤销对应 self-save 标记；
- Save As 到当前同一路径时使用路径等价判断，而不是原始字符串比较。

涉及源码：

- `packages/desktop/src/main/filesystem/watcher.ts`
- `packages/desktop/src/main/app/windowManager.ts`
- `packages/desktop/src/main/menu/actions/file.ts`

详细问题链路、失败尝试、诊断日志和维护约束见：

`docs/custom/文件保存与Watcher自触发问题说明.md`

## 5. Windows 安装器自定义

Windows 安装器自定义入口：

- `packages/desktop/build/windows/installer.nsh`

当前该文件同时负责：

- 原有 Markdown 默认文件关联询问
- Markdown 文件 `Open with MarkText`
- 文件夹本身 `Open with MarkText`
- 卸载时清理对应注册表项

electron-builder 配置通过：

```text
nsis.include = windows/installer.nsh
```

把该脚本包含进 NSIS 安装包。

## 6. Windows x64 构建方式

当前优先使用已经实际验证的“两阶段构建”流程：

```powershell
cd E:\github\marktext
pnpm run build

cd .\packages\desktop
npx --yes electron-builder@26.0.3 --win nsis --x64 --publish never
```

原因是项目自带的完整 Windows 打包脚本曾在 electron-builder 的 node modules 扫描阶段长时间卡住。

因此：

- 两阶段方式是当前首选；
- `pnpm run build:win:x64` 保留为原项目官方入口，但不是本 fork 的首选本地打包方式；
- Windows 右键菜单属于 NSIS 安装器逻辑，只有完成第二阶段并安装生成的 setup EXE 后才会注册；`pnpm run dev` 本身不会创建这些右键菜单。

完整说明见：

`docs/custom/Windows_x64本地编译指南.md`

## 7. 后续功能记录规则

以后新增重要功能时，建议：

1. 单独建立 `docs/custom/<功能名>实现记录.md`；
2. 在本文件“已实现的自定义功能”中增加一项；
3. 记录涉及的完整源码路径；
4. 记录设计目标、兼容性与性能约束；
5. 如果涉及 Windows 安装或打包，更新编译指南。

这样 AI 在进入仓库后，通过根目录 `AGENTS.md` 和本文件即可迅速建立正确项目背景。
